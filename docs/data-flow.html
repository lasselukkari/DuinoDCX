🎯 Overview: The 30-Second Version

The Journey of a Byte (TL;DR):
  1. Hardware: DCX2496 sends bytes over RS-232 serial cable
  2. ESP32/Mac: Reads serial data, broadcasts via Server-Sent Events (SSE)
  3. Browser: Receives SSE stream, passes to parser
  4. Parser: Decodes 7-to-8 bit encoding, extracts parameter values
  5. Store: Holds the complete device state as JavaScript object
  6. React: Components subscribe to store, render as HTML
🍕 Pizza Delivery Analogy:
Think of it like ordering pizza online. Your pizza (data) travels from the kitchen (DCX2496), through roads (serial cable), to a dispatcher (ESP32), who broadcasts updates (SSE) to your phone (browser). The app (React) shows you where your pizza is on a map (the UI).

Layer 1: The Physical Wire (RS-232 Serial)

The Behringer DCX2496 is a professional audio processor from the early 2000s. It communicates using RS-232 serial - the same technology your grandpa's modem used!

An ESP32 microcontroller sits between the DCX2496 and your network. It reads bytes from the serial port and serves a web interface. The ESP32 is like a translator between the old world (serial) and the new world (WiFi/HTTP).

The RS-232 cable is like a really old landline telephone. The ESP32 is like one of those VoIP adapters that lets your old phone work with modern internet.

Layer 2: SysEx Protocol (MIDI Messages)

The DCX2496 speaks MIDI SysEx (System Exclusive messages). Even though it's connected via RS-232 (not USB MIDI), it uses the same message format.

📦 SysEx Message Structure

F0 00 20 32 [DeviceID] [ModelID] [Command] ... data ... F7
│  └─────┬─────┘    │         │        │              │
│        │          │         │        │              └─ End byte
│        │          │         │        └─ What to do (e.g., 0x10 = dump response)
│        │          │         └─ 0x0E = DCX2496
│        │          └─ Usually 0x00
│        └─ Behringer's manufacturer ID
└─ Start byte (0xF0 = SysEx start)

Key commands the device uses:

CommandHexDescription
Search/Ping0x40Find devices on the wire
Dump Response0x10Device sends its current state
Direct Change0x20Change a single parameter
Request Dump0x50Ask device to send its state
📧 Email Analogy:
SysEx is like an email format. F0 is "Dear Sir/Madam", the vendor ID is the return address, the command is the subject line, the data is the message body, and F7 is "Sincerely, DCX2496".

Layer 3: 7-bit to 8-bit Decoding

Here's where it gets interesting! MIDI was designed in the 1980s when memory was expensive. The protocol only allows values 0-127 per byte (7 bits). But real data needs 0-255 (8 bits)!

🔢 The Problem

MIDI bytes must have the high bit = 0 (values 0x00-0x7F). But the device wants to send the value 0xA5 (165) which has the high bit = 1!

💡 The Solution: Block Encoding

Every 7 data bytes are packed into 8 wire bytes:

Wire bytes:  [byte0] [byte1] [byte2] [byte3] [byte4] [byte5] [byte6] [msbByte]
              0x25    0x33    0x41    0x00    0x00    0x00    0x00    0x01
               │                                                        │
               └── Lower 7 bits of data (0x25)                         │
                                                        MSB flag byte ──┘
                                                        (bit 0 = 1 = byte0 has MSB set)

Real value: byte0 = 0x25 | 0x80 = 0xA5 ✓

The decoder extracts the MSBs from the 8th byte and restores them to bytes 1-7:

// Simplified decoding logic
for each block of 8 bytes:
    msbByte = block[7]
    for i = 0 to 6:
        if (msbByte has bit i set):
            block[i] |= 0x80  // Restore high bit
🧳 Luggage Analogy:
Imagine airline rules say each bag can only weigh 70 lbs. But you have items weighing up to 100 lbs. So you pack 7 bags with 70 lbs each, then put the "overflow weight" in an 8th bag. At your destination, you combine them back to get your original 100 lb items.

Layer 4: Edit Buffer Parsing

After decoding, we have raw 8-bit data (~1659 bytes for the edit buffer). Now we need to understand what each byte means.

🗺️ The Edit Buffer Map

The DCX2496's edit buffer is organized in a specific structure:

SectionByte RangeContains
Header0-78Signatures, metadata
Preset Name79-868-character ASCII name
Setup87-120Output config, delays, mutes
Input A121-244EQ, dynamics, gain
Input B245-368EQ, dynamics, gain
Input C369-492EQ, dynamics, gain
Input Sum493-616EQ, dynamics, gain
Outputs 1-6617-1500+Crossovers, EQ, limiters

The parser reads bytes sequentially and builds a JavaScript object:

// Pseudo-code for parsing
const state = {
  setup: {
    outputConfig: readWord(offset + 0),   // 0=Mono, 1=LMH-LMH, etc.
    airTemperature: readWord(offset + 2), // 40 = 20°C
  },
  inputs: {
    A: {
      gain: (readWord(offset + 10) - 150) / 10, // 150 = 0dB
      mute: readWord(offset + 11) === 1,
      equalizers: [...],
    },
    // B, C, Sum...
  },
  outputs: { /* 1-6 */ },
};
📄 Spreadsheet Analogy:
The raw bytes are like a CSV file with no headers. The parser is like someone who knows "column A is names, column B is ages, column C is salaries" and creates a proper labeled spreadsheet from the raw data.

Layer 5: The State Store

The parsed state is stored in a centralized store (like Redux, but simpler). This is the "single source of truth" for the entire application.

🏪 The Store Pattern

// dcx-store.ts (simplified)
const dcxStore = {
  state: null,  // The device state object
  listeners: [],
  
  setFullState(newState) {
    this.state = newState;
    this.notify();  // Tell everyone the state changed!
  },
  
  subscribe(listener) {
    this.listeners.push(listener);
    return () => { /* remove listener */ };
  },
  
  notify() {
    for (const listener of this.listeners) {
      listener();  // "Hey! State changed!"
    }
  }
};

When you change a parameter on the device (like turning a knob), it sends a 0x20 (Direct Change) message. The store applies this update and notifies all listeners.

📻 Radio Station Analogy:
The store is like a radio station. React components are radios tuned to that station. When the station broadcasts new music (state change), all radios automatically play it.

⬇️

Layer 6: React Components → HTML

Finally, React components subscribe to the store and render HTML. When the store updates, React automatically re-renders the affected components.

⚛️ The useDcxState Hook

// In your component
function GainSlider({ channelId }) {
  const { state } = useDcxState(connection);
  
  if (!state) return <p>Loading...</p>;
  
  const gain = state.inputs[channelId].gain;
  
  return (
    <input 
      type="range" 
      value={gain} 
      min={-15} 
      max={15} 
      step={0.1}
    />
  );
}

The HTML output might look like:

<input type="range" value="0" min="-15" max="15" step="0.1">
🎭 Theater Analogy:
React components are like stage actors. The script (state) tells them what to say. When the script changes, they instantly change their lines. The audience (you) sees the new performance (updated HTML) without any visible transition.

Example: Following a Gain Value End-to-End

Let's trace Input A's gain value from wire to screen:

🔬 Step-by-Step Trace

1. On the wire (serial bytes):

F0 00 20 32 00 0E 10 00 ... 16 00 00 00 00 00 00 00 ... F7
                            │
                            └─ 0x16 = 22 (7-bit encoded)

2. After 7-to-8 decoding:

... 96 00 ...
    │
    └─ 0x96 = 150 (high bit restored: 22 | 0x80 = 150)

3. Parser extracts value:

// At byte offset 130 (Input A gain position)
const rawGain = data[130] | (data[131] << 8);  // = 150
const gain = (rawGain - 150) / 10;              // = 0.0 dB

4. Store holds state:

dcxStore.state = {
  inputs: {
    A: { gain: 0.0, mute: false, ... },
    ...
  }
};

5. React renders HTML:

<FormLabel>A. Input A</FormLabel>
<input type="range" value="0" ... />
<span>0.0 dB</span>
