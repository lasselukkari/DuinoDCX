📦 Introduction

Imagine you want to know the volume level of a speaker connected to a DCX2496 unit. The device knows the answer, but it speaks a weird alien language called "MIDI SysEx". Our job is to get that answer, translate it, and put it on your screen.

The Analogy: The Postal Service Think of the data flow as a letter being delivered. The Wire is the mail truck. The Parser is the person who opens the envelope and translates the letter. The State is a clipboard where we write down the important info. The UI is a big display board that reads from the clipboard.
⬇

🚛 Layer 1: The Wire format

The data travels from the device to your computer over a serial cable. But there's a catch: the road is old and bumpy. It can only handle small packages.

The 7-bit Limit

Standard computer data uses 8 bits (like having 8 fingers to count on, allowing numbers 0-255). But MIDI, the protocol used by the DCX, is from the 80s. It only allows 7 bits (0-127).

So, if the device wants to send the number 150 (which needs 8 bits), it has to chop it up. This is like tearing a page of a letter in half to fit it into two smaller envelopes.

Animation: 7-to-8 Bit Decoding

Watch how the "MSB Byte" (Byte #7) distributes its bits to complete the other 7 bytes. This reassembles the full 8-bit values.

The Container (SysEx)

The data doesn't just travel naked. It's wrapped in a container called a "SysEx Message".

F0
00
20
32
...DATA...
F7
  • F0: "Start of message" (The opening of the envelope)
  • 00 20 32: "To Behringer" (The address)
  • ...DATA...: The actual settings (The chopped up letter)
  • F7: "End of message" (The seal)
⬇

🧩 Layer 2: The Parser (The Translator)

This layer lives in dcx-parser-new. Its job is to open the envelope and tape the pages back together.

Step 1: Unwrap and Glue

First, we strip off the F0... wrapper. Then we run a "7-to-8 bit decode". We take those chopped-up 7-bit bytes and stitch them back into normal 8-bit bytes.

Step 2: The Map

Now we have a long string of numbers, like: ... 02 01 96 ...

How do we know which number is "Input A Gain"? We use a Map (Offsets). We know that for Input A: 

Input A Gain is always at Byte Offset #24
Input A Mute is always at Byte Offset #25

So the parser counts 24 steps into the data, grabs the number (let's say it finds 150), and attaches a label to it: gain: 150.

⬇

📋 Layer 3: The State (The Clipboard)

Once parsed, we don't just throw the data at the screen. We store it in a central place called the State. This lives in the React application (dcx-ui).

The State is a big JavaScript object that looks like this: 

{
  "inputs": [
    {
      "channel": "A",
      "gain": 150,     // Raw value
      "mute": false
    },
    ...
  ]
}

This is our "Single Source of Truth". The app useDcxState hook watches the parser. Every time a new message is parsed, it updates this clipboard.

⬇

🖥️ Layer 4: The UI (The Display)

Finally, the React components (like inputs.tsx) read from the State.

The Conversion

Wait, the state says gain: 150 using a raw value. That doesn't mean anything to a human! The UI (or sometimes the parser helper) needs to convert it.

The conversion rule: (Value - 150) / 10 = dB

So: (150 - 150) / 10 = 0.0 dB

If the raw value was 160: (160 - 150) / 10 = +1.0 dB

The Render

The component paints <div>+1.0 dB</div> on your screen. When you click a button to change it, the whole process happens in reverse: UI → State → Parser (Encoder) → Wire.
